# Lab：測試自動化工程師（test-automation-engineer）

- **模組**：10　**能力層**：L2　**建議時間**：25 分鐘（課堂）＋ 作業延伸
- **前置**：已安裝 `test-automation-engineer.md`。準備一個有 2～3 步流程的網頁（登入、表單、購物車皆可）。

---

## 練習 1：抓 flaky 來源（L2）

1. 給 Agent 一段「壞掉的」E2E 測試（可請它先產一個 Before 版本：用 sleep、脆弱選擇器、共用資料）。
2. 要求它列出「這個測試在 CI 上會 flaky 的所有原因」並分類。
3. 對每個原因，要它給「修正（不是繞過）」。

**評分要點**
- ✅ 抓到時間式等待、共用狀態、脆弱選擇器三大類
- ❌ 建議「加重試」→ 追問：重試是讓它過，還是量測它有多不穩？

---

## 練習 2：重寫成決定性版本（L2）

1. 要求 Agent 把測試改寫成：透過 API 建資料、角色式選擇器、等網路回應而非時間。
2. 檢查：改寫後還有沒有任何 `waitForTimeout`？資料還依賴 seed 嗎？
3. 讓學員說明「為什麼透過 API 設定、透過 UI 斷言」比「每個測試都走登入表單」好。

**評分要點**：學員能指出「登入 200 次 = 200 次在已測過的頁面上 flaky 的機會」。

---

## 練習 3：金字塔判斷（L2）

1. 給 5 個測試情境（例：「驗證 email 格式」「結帳成功導向確認頁」「按鈕 hover 變色」…）。
2. 要求 Agent 判斷每個該放在單元 / API / E2E 哪一層，並說明理由。
3. 討論：一個「40 個瀏覽器測試 vs 40 個單元測試」的驗證矩陣，成本差多少？

**評分要點**：學員理解「E2E 是頂端不是全部，每個 E2E 測試都要為它的瀏覽器辯護」。

---

## 繳交

- 練習 1 的 flaky 原因清單（含分類與修正）
- 練習 2 的決定性版測試
- 練習 3 的分層判斷表 + 100 字內反思：
  你團隊的測試套件，大家信任它到「紅燈就擋合併」嗎？為什麼
