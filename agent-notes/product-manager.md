- **能力層**：L2→L3（會驗 → 會編）
- **對應 Agent 定義**：[`AI-to-Agent-Agency-zh-TW` / `agents/product/product-manager.md`](https://github.com/draiagent/AI-to-Agent-Agency-zh-TW/blob/main/agents/product/product-manager.md)

## 1. 定位：這個 Agent 解決什麼問題

模組 1、2 的數位員工各自把一個職能做好。產品經理是**把這些職能編派成一條有成果的線**的人：
從探索 → 機會評估 → PRD → 上市 → 衡量。它也是課程裡第一個明確「以成果（outcome）
而非產出（output）」思考的角色——「出貨了卻沒人用的功能不是勝利，是有部署時間戳的浪費」。

它的三條鐵律最值得教：**從問題出發不從解法出發**、**寫 PRD 前先寫新聞稿**、
**沒有負責人＋成功指標＋時間範圍就不是藍圖項目**。

一句話：**它把「大家各做各的」提升到「一條對齊的、有明確成功衡量的產品線」。**

### 什麼時候召喚它

- 有個功能請求，要先釐清背後的使用者痛點與商業目標
- 要寫 PRD、機會評估、產品藍圖、GTM 計畫
- 團隊在做什麼、為什麼做、成功怎麼衡量說不清楚
- 要對一堆需求做優先排序（RICE）

### 什麼時候「不要」召喚它

- 是「使用者到底要什麼」的一手研究 → ux-researcher
- 是「這個 sprint 裝哪些故事」的細粒度排程 → sprint-prioritizer
- 是純技術架構取捨 → backend-architect

## 2. Before / After 示範

**任務**：「業務說大客戶要匯出功能，幫我規劃。」

### Before（無 Agent）

> 產出：一份「匯出功能 PRD」，直接開始寫欄位與格式。沒問是誰要、多常要、
> 不做的代價、成功指標是什麼。做完可能沒人用。

### After（召喚 product-manager）

> 會先反問並產出：
> - 問題陳述：誰遇到、多常、不解決的代價；要證據（訪談 n=？、行為資料、客服訊號）
> - 目標與成功指標表（基線 → 目標 → 衡量期間）
> - 非目標：這次「不」做什麼
> - RICE 分數；考慮過的選項（完整／MVP／買／延後）
> - 建議：建置／探索／延後／砍，附理由與「什麼會改變這個決定」

**課堂提問**：讓學員指出「Before 直接寫 PRD 的三個風險」，以及 After 的哪一項
最能防止「做了沒人用」（提示：成功指標 + 證據）。

## 3. 怎麼帶學員「驗收」它的產出

| 檢核點 | 有 / 無 |
|---|---|
| 從「問題」開始，不是從「解法」開始 | |
| 問題陳述有證據（訪談／行為資料／客服／競爭），不是「感覺客戶想要」 | |
| 每個目標都有指標 + 基線 + 目標值 + 衡量期間 | |
| 有「非目標」段落，明講這次不做什麼 | |
| 有優先排序依據（RICE 或同等） | |
| 藍圖項目都有負責人 + 成功指標 + 時間範圍 | |
| 有「我們不做什麼、為什麼」的清單 | |

若成功指標那格是空的、或全是形容詞 → 退回。

## 4. 常見誤區

1. **拿到功能請求就寫 PRD。** 鐵律第 1 條：先找底層痛點或商業目標。
2. **藍圖當承諾。** 它是「有優先序的押注」，不是合約。
3. **只列要做的，不列不做的。** 「不做什麼、為什麼」和藍圖一樣重要。
4. **對齊誤當同意。** 不需要全體同意才前進，需要每個人理解決策與自己的角色。
5. **無聲吸收範疇變更。** 每個變更請求都要記錄、評估、接受/延後/拒絕。

## 5. 銜接其他 Agent

ux-researcher 給使用者證據 → **product-manager 決定做什麼、成功怎麼衡量** →
sprint-prioritizer 決定「這個 sprint 先裝哪幾個」→ 工程數位員工執行 →
product-manager 在 30/60/90 天回頭看指標。在模組 3，PM 是那個把整條線串起來、
並持有「成果」這把尺的人。
