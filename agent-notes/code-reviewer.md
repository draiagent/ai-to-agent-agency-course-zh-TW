# 教學導引：程式碼審查者（code-reviewer）

- **模組**：2 — 工程實作四人組
- **能力層**：L2（會驗）— 把「會驗」制度化成一道關卡
- **對應 Agent 定義**：[`AI-to-Agent-Agency-zh-TW` / `agents/engineering/code-reviewer.md`](https://github.com/draiagent/AI-to-Agent-Agency-zh-TW/blob/main/agents/engineering/code-reviewer.md)

---

## 1. 定位：這個 Agent 解決什麼問題

前兩個 Agent（backend-architect、frontend-developer）教學員「針對單一產出做驗收」。
程式碼審查者把這件事**變成流程裡的固定關卡**：每次有變更，就過一次同樣的檢查清單，
分優先級（🔴 阻擋 / 🟡 建議 / 💭 小建議），而且**每則留言都要解釋原因**。

它也示範了一個對學員很重要的觀念：**審查是教學，不是把關。** AI 給的審查若只會說
「這裡不好」，價值很低；能說「為什麼不好、可以怎麼改、為什麼那樣改更好」才有用。

一句話：**它把「一次性驗收」變成「可重複的品質關卡」。**

### 什麼時候召喚它

- 任何 AI 產出的程式碼要進正式專案前
- 想幫團隊建立 PR 審查清單
- 學員自己寫的程式碼想要一份帶教學性質的回饋

### 什麼時候「不要」召喚它

- 還在探索、寫拋棄式原型 → 先別審，用 rapid-prototyper
- 問題是「架構該怎麼設計」而非「這段實作對不對」→ backend-architect

## 2. Before / After 示範

**任務**：「幫我看一下這段登入 API。」

### Before（無 Agent，隨口請 AI 看）

> 回饋：「看起來還行，可以加點註解，變數名可以更清楚。」——沒有分優先級，
> 沒有抓到真正的問題，學員不知道哪些非改不可。

### After（召喚 code-reviewer）

> 回饋會是：
> - **總結**：整體結構清楚，但有 1 個阻擋項、2 個建議
> - 🔴 **第 42 行 SQL 注入**：使用者輸入直接內插進查詢 → 原因 → 改用參數化查詢
> - 🟡 缺少對 `email` 的輸入驗證
> - 🟡 密碼比對失敗與帳號不存在回傳不同訊息（帳號列舉風險）
> - 💭 `pwd` 建議改名 `passwordHash`
> - **結語**：修掉 🔴 就可以合併，🟡 建議這輪一起處理

**課堂提問**：讓學員指出「Before 的回饋為什麼幾乎沒用」，以及 After 的哪一則留言
最有教學價值（提示：有「原因」那一則）。

## 3. 怎麼帶學員用它（把它當關卡）

給學員一段有明顯問題的程式碼（老師預先埋 1 個安全問題、1 個效能問題、1 個命名問題），
請他們召喚 code-reviewer，然後檢查它的回饋：

| 檢核點 | 有 / 無 |
|---|---|
| 開頭有總結（整體印象 + 主要疑慮 + 優點） | |
| 每個問題都有優先級標記（🔴/🟡/💭） | |
| 每則留言都有「原因」，不只是「改這個」 | |
| 用建議語氣（「可以考慮…」）而非命令 | |
| 有抓到老師埋的安全問題（🔴） | |
| 有點出至少一個做得好的地方 | |
| 一次給完，沒有說「還有其他問題之後再說」 | |

## 4. 常見誤區

1. **把審查當成風格糾察。** Agent 定義開宗明義：聚焦正確性、安全、可維護性、效能，
   **不是 tab 還是空格**。學員若拿它挑排版，方向就錯了。
2. **無條件照做所有留言。** 🟡 和 💭 是建議，要學員自己判斷取捨；只有 🔴 是必須。
3. **只看結論不看原因。** 這個 Agent 的教學價值全在「為什麼」，跳過就浪費了。
4. **一次只丟一小段。** 給的上下文太少，它只能給籠統回饋；要給完整的變更。

## 5. 銜接其他 Agent

backend-architect 出設計 → 有人實作 → **code-reviewer 對照設計審實作** →
**devops-automator** 才把它部署出去。在模組 2，code-reviewer 是「擋在上線前」的那道關。
到模組 5 會再把它跟 security-engineer、test-writer 組成更完整的治理流程。
