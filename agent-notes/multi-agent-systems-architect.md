# 教學導引：多代理系統架構師（multi-agent-systems-architect）

- **模組**：1 — 工程（本模組的收尾與最高點）
- **能力層**：L3→L4（會編 → 會養）
- **對應 Agent 定義**：[`AI-to-Agent-Agency-zh-TW` / `agents/engineering/multi-agent-systems-architect.md`](https://github.com/draiagent/AI-to-Agent-Agency-zh-TW/blob/main/agents/engineering/multi-agent-systems-architect.md)

## 1. 定位：這個 Agent 解決什麼問題

前面幾位數位員工，學員學會了「單一 Agent 怎麼定義、怎麼驗收、怎麼上線」。
但真實工作是**一群 Agent 協作**——這時問題不再是「提示寫得好不好」，而是分散式系統問題：
一個代理逾時怎麼辦？兩個代理結論矛盾誰說了算？上下文一路累積爆掉怎麼辦？
壞輸出怎麼追回到是哪個代理造成的？

多代理系統架構師的核心信念是：**Demo 會騙人；正式環境才說真話。** 它逼你把
「五個代理串一串就說做完了」升級成「有拓撲圖、有失敗模式清單、有備援鏈、有 HITL 關卡、
有 trace_id」的真正架構。

一句話：**它把「一堆 Agent 湊在一起」提升到「一個可治理、撐得住的分散式系統」。**

### 什麼時候召喚它

- 要設計「多個 Agent 分工」的流程，超過 2～3 個 Agent
- demo 版多代理流程要走向正式環境
- 多代理系統偶發失敗、結果不穩、難以除錯
- 要決定拓撲（循序／扇出扇入／階層式／評估器迴圈／網狀）

### 什麼時候「不要」召喚它

- 只有單一 Agent 的任務 → prompt-engineer / ai-engineer
- 還在驗證「這個點子行不行」的原型階段 → 先別上架構
- 問題其實是某一個 Agent 的提示不穩 → prompt-engineer

## 2. Before / After 示範

**任務**：「我想做一個『研究 → 分析 → 寫報告』的三 Agent 流程。」

### Before（無 Agent）

> 產出：Agent A 的輸出丟給 B，B 丟給 C，C 出報告。demo 能跑。
> 但：B 逾時整條停；A 的來源錯了 C 也不知道；三個代理的上下文一路累積；
> 報告出錯無法判斷是誰的問題。

### After（召喚 multi-agent-systems-architect）

> 產出會包含：
> - 拓撲圖 + 為什麼選循序（而非扇出）的理由
> - 每個代理的輸入／輸出契約，以及「不負責什麼」
> - 失敗模式表：硬失敗、無聲失敗、矛盾、連鎖失敗各自的偵測與復原
> - 每個代理的備援鏈（主要 → 縮限 → 降級 → 人類）
> - 上下文策略：傳摘要不傳全文、結構化狀態物件
> - 可觀測性：每次呼叫帶共用 trace_id 的結構化日誌
> - HITL 關卡放在哪（例如「寄出報告」前）
> - 部署前的評測要求（每個代理 ≥20 案例）

**課堂提問**：讓學員指出 Before 版本裡「至少 3 個在 demo 看不出、但正式環境一定會炸的點」。

## 3. 怎麼帶學員「驗收」它的產出

| 檢核點 | 有 / 無 |
|---|---|
| 有拓撲圖，且有「為什麼是這個拓撲」的理由（預設階層式，用網狀要辯護） | |
| 每個代理有輸入／輸出契約 + 「不負責什麼」 | |
| 失敗模式被逐一列出，每個都有偵測 + 復原路徑 | |
| 每個代理都有備援鏈，系統「永遠產出某個東西」 | |
| 有上下文預算計算，且不會無聲截斷必要欄位 | |
| 每次代理呼叫有帶共用 trace_id 的結構化日誌 | |
| 不可逆／高影響／低信心的動作前有 HITL 關卡 | |
| 有部署前的評測要求（代理層 + 管線層） | |

少於 6 項打勾 → 這還是 demo，不是架構，退回。

## 4. 常見誤區

1. **一開始就用網狀（mesh）。** 定義明講：網狀是最難除錯的拓撲，預設用階層式。
2. **只設計正常路徑。** 「我跑的時候能動」不是設計。失敗模式沒列完就不算數。
3. **上下文放到爆。** 學員常把每個代理的完整輸出往下傳，5 跳後就爆視窗。要傳摘要 + 結構化狀態。
4. **沒有 trace_id。** 追不回「哪個代理造成錯誤」的系統，等於沒上線。
5. **HITL 關卡亂放。** 全部都要人核准 → 人開始橡皮圖章；都不要 → 出事沒人擋。要按不可逆性／影響範圍／信心來放。

## 5. 銜接：這是模組 1 的總結

模組 1 的七位數位員工合起來就是一個完整的心智模型：

- prompt-engineer：Agent = 固定下來的規格
- ai-engineer：判斷這任務該不該用 AI、用哪種
- backend-architect / frontend-developer / code-reviewer / devops-automator：單一領域的產出、驗收與上線
- **multi-agent-systems-architect：把以上這些「組成一個撐得住的系統」**

學員做完這一課，就具備看懂後面每個部門「數位員工怎麼被編派成團隊」的框架。
