## 1. 定位：這個 Agent 解決什麼問題

prompt-engineer 教「怎麼把提示寫成規格」，但更前面有個問題：**這個任務適合用 AI 嗎？
用 LLM、傳統 ML、還是根本不該用模型？** AI 工程師負責回答這個。

它的判準是務實的：延遲要求、資料量、準確率門檻、每次預測的成本、能不能量測漂移、
倫理與偏誤風險。學員最常見的錯誤是「什麼都想丟給 LLM」，這個數位員工會把
「即時 / 批次 / 串流 / 邊緣 / 混合」五種整合模式攤開，逼你選一個並說理由。

一句話：**它把「這個我要用 AI 做」提升到「這個任務的正確工具是 X，因為延遲／成本／資料」。**

### 什麼時候召喚它

- 要決定某功能用 LLM、傳統 ML、還是規則就好
- 要設計資料管線、MLOps、模型監控與重新訓練
- 要評估「推論延遲 / 每次預測成本」撐不撐得住產品規模
- 要做偏誤測試、隱私保護、可解釋性

### 什麼時候「不要」召喚它

- 提示本身要調穩 → prompt-engineer
- 是「多個 AI 角色怎麼協作」的問題 → multi-agent-systems-architect
- 純後端系統設計、跟模型無關 → backend-architect

## 2. Before / After 示範

**任務**：「我想做一個自動判斷客訴嚴重度的功能。」

### Before（無 Agent）

> 產出：「用 GPT 分類就好。」——沒問資料量、延遲要求、錯判成本、要不要可解釋、
> 每天幾萬筆的 API 費用。

### After（召喚 ai-engineer）

> 會反問並給出決策：
> - 每天量多少？即時還是可批次？錯判把嚴重當普通的代價多大？
> - 若量大、要即時、要低成本、有標註資料 → 建議傳統分類模型 + LLM 只做疑難案例
> - 若量小、要快上線、可容忍成本 → LLM few-shot
> - 附：漂移監控怎麼設、偏誤測試跨哪些族群、每次預測成本估算

**課堂提問**：讓學員說出「同一個功能，為什麼在不同的量／延遲／成本條件下，答案不一樣」。

## 3. 怎麼帶學員「驗收」它的產出

| 檢核點 | 有 / 無 |
|---|---|
| 有問清楚：資料量、延遲要求、準確率門檻、錯判成本 | |
| 在 LLM / 傳統 ML / 規則之間有明確選擇**與理由** | |
| 有指定整合模式（即時／批次／串流／邊緣／混合） | |
| 有講「每次預測成本」與規模的關係 | |
| 有漂移偵測 + 重新訓練的計畫 | |
| 有偏誤 / 隱私 / 可解釋性的考量 | |

## 4. 常見誤區

1. **一律用 LLM。** 這個 Agent 存在的意義之一，就是擋掉「用大模型做小事」。
2. **忽略成本與延遲。** demo 能跑不代表產品規模下划算；要看每次預測成本 × 量。
3. **上線就結束。** 定義強調漂移偵測與自動重新訓練——模型會退化，沒監控等於沒上線。
4. **偏誤測試當形式。** 要明確跨哪些人口族群、用什麼公平性指標。
