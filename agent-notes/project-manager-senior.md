# 教學導引：資深專案經理（project-manager-senior）

- **模組**：5 — 專案管理
- **能力層**：L2→L3（會驗 → 會編）
- **對應 Agent 定義**：[`AI-to-Agent-Agency-zh-TW` / `agents/project-management/project-manager-senior.md`](https://github.com/draiagent/AI-to-Agent-Agency-zh-TW/blob/main/agents/project-management/project-manager-senior.md)

---

## 1. 定位：這個 Agent 解決什麼問題

product-manager（模組 3）決定「做什麼、成功指標」。資深專案經理更下游一層：
**把規格拆成「開發者 30–60 分鐘能做完、有驗收標準」的任務清單。**

它最值得教的一點是**對範疇務實**——不加規格裡沒有的「豪華」「高級」需求、
不做鍍金、引用規格的確切文字。它把「AI 幫我想像一個很完整的專案」拉回
「規格實際上要求什麼」。

一句話：**它把「模糊的規格」提升到「可執行、可驗收、不蔓延的任務清單」。**

### 什麼時候召喚它

- 有一份規格，要拆成開發任務
- 需求不清或有缺漏，要標出來
- 專案常常做超過規格範圍（範疇蔓延）
- 要把技術堆疊要求從規格中擷取出來

### 什麼時候「不要」召喚它

- 是「這個功能該不該做」的策略問題 → product-manager
- 是「這個 sprint 裝哪幾個」的產能排程 → sprint-prioritizer
- 是會議中的決議與行動項擷取 → meeting-notes-specialist

## 2. Before / After 示範

**任務**：「這是客戶的網站規格，幫我開始做。」

### Before（無 Agent）

> 產出：直接開始寫程式碼，順手加了動畫、深色模式、會員系統——規格裡都沒有。
> 沒有任務清單，做到一半才發現漏了規格第 3 節的表單。

### After（召喚 project-manager-senior）

> 會產出：
> - 規格摘要：引用關鍵要求的**確切文字**、技術堆疊、目標時程
> - 逐項開發任務，每個含：描述、驗收標準（Given/When/Then）、要改的檔案、對應規格章節
> - 明確標出缺漏或不清楚的要求
> - 品質要求清單（響應式、表單功能、圖片來源…）

**課堂提問**：讓學員指出「Before 加的哪三樣東西是規格沒要求的」，以及
「驗收標準」欄位如何讓任務可被驗收。

---

## 3. 怎麼帶學員「驗收」它的產出

| 檢核點 | 有 / 無 |
|---|---|
| 規格摘要引用了**原文**，不是改寫 | |
| 每個任務都有驗收標準（可測試） | |
| 每個任務大小合理（開發者 30–60 分鐘可做完） | |
| 沒有規格裡沒有的「豪華」需求 | |
| 缺漏或不清楚的要求有被標出來 | |
| 有列出對應的規格章節（可回溯） | |

若出現規格沒提的功能、或任務大到「做兩天」→ 退回。

---

## 4. 常見誤區

1. **讓 AI 自由發揮補完規格。** 它的價值是「忠於規格」，不是「想像一個更完整的專案」。
2. **任務顆粒度太粗。** 「做完前端」不是任務；「建立首頁版面，含頁首/內容/頁尾」才是。
3. **沒有驗收標準。** 沒有 Given/When/Then 的任務無法判斷「做完了沒」。
4. **忽略缺漏。** 規格不清楚的地方要標記給客戶，不是自己猜。

---

## 5. 銜接其他 Agent

product-manager（決定做什麼）→ **project-manager-senior（拆成任務清單）** →
sprint-prioritizer（排進 sprint）→ 工程數位員工（backend-architect / frontend-developer…）執行。
在模組 5，這位是「把規格變成可執行工作」的那一棒。
