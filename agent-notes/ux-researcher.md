# 教學導引：UX 研究員（ux-researcher）

- **模組**：2 — 設計
- **能力層**：L1→L2（會派 → 會驗）
- **對應 Agent 定義**：[`AI-to-Agent-Agency-zh-TW` / `agents/design/ux-researcher.md`](https://github.com/draiagent/AI-to-Agent-Agency-zh-TW/blob/main/agents/design/ux-researcher.md)

## 1. 定位：這個 Agent 解決什麼問題

在 ui-designer「把東西做漂亮」之前，有個更前面的問題：**使用者到底要什麼？我們的假設對嗎？**
UX 研究員負責用資料回答，而不是靠團隊拍腦袋。

它的核心信念是**研究方法論優先**——先確立研究問題，再選方法；用適當樣本數；
用三角驗證；客觀呈現、不帶確認偏誤。學員最常見的錯誤是「拿 AI 生一堆 persona 就當研究」——
這個數位員工會逼你先回答「這份 persona 背後有幾場訪談、幾份問卷、幾個行為資料點」。

一句話：**它把「我覺得使用者會……」提升到「基於 N 個資料點，使用者實際……」。**

### 什麼時候召喚它

- 要規劃使用者研究（訪談、問卷、可用性測試）
- 要把零散的使用者回饋整理成 persona／旅程地圖／可執行建議
- 團隊在爭論「使用者要不要這個功能」，需要驗證
- 要設計可用性測試的腳本與任務情境

### 什麼時候「不要」召喚它

- 已經知道要做什麼、只差視覺 → ui-designer
- 是「這個功能該排在哪個 sprint」的優先序問題 → sprint-prioritizer（模組 3）

## 2. Before / After 示範

**任務**：「幫我做我們 App 的使用者研究。」

### Before（無 Agent）

> 產出：三個聽起來合理的 persona，配一段「使用者重視效率與簡潔」。
> 沒有研究問題、沒有方法、沒有樣本、沒有一句真實引言——本質是想像。

### After（召喚 ux-researcher）

> 會反問並產出：
> - 研究問題是什麼？想影響哪個產品決策？成功指標？
> - 建議方法（質性／量化／混合）與理由、樣本數與招募條件
> - 可用性測試腳本：任務情境、成功標準、要觀察的行為、放聲思考
> - persona 範本會標「基於 X 訪談、Y 問卷、Z 行為資料點」
> - 建議分高／中／長期優先，每條附影響、工作量、成功指標

**課堂提問**：讓學員指出「Before 的 persona 為什麼不能拿來做決策」，
以及 After 的哪一項讓研究結果站得住腳（提示：研究問題 + 樣本 + 真實引言）。

## 3. 怎麼帶學員「驗收」它的產出

| 檢核點 | 有 / 無 |
|---|---|
| 先有「研究問題」與「想影響的決策」，才選方法 | |
| 方法選擇有理由，樣本數有依據 | |
| 有偏誤防範（篩選、招募多元性、不帶確認偏誤） | |
| persona／發現都標了「基於多少資料」 | |
| 建議是可執行的（有具體行動、影響、成功指標），不是「要更好用」 | |
| 有三角驗證（多重資料來源） | |
| 有無障礙／包容性的研究考量 | |

若「基於多少資料」那格是空的 → 這是想像，不是研究，退回。

---

## 4. 常見誤區

1. **拿 AI 生 persona 當研究。** persona 是研究的「輸出」，不是「輸入」。沒有資料的 persona 是虛構角色。
2. **先選方法再想問題。** 定義明講「先確立研究問題」。方法要服務問題。
3. **只做質性或只做量化。** 「幾個人有這問題」要量化，「為什麼」要質性，通常都要。
4. **建議寫成形容詞。** 「介面要更直覺」不是建議；「把 X 步驟從 3 頁併成 1 頁」才是。

## 5. 銜接其他 Agent

**ux-researcher（使用者要什麼、假設對不對）** → ui-designer（做成設計系統）→
frontend-developer（實作）。在模組 2，UX 研究員示範「研究」這個職能怎麼被規格化——
它的產出（研究問題、方法、樣本、可執行建議）本身就是一份可驗收的規格。
到模組 3，它的發現會餵給 product manager 做功能決策。
