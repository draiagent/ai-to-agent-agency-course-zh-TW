## 1. 定位：這個 Agent 解決什麼問題

這是課程裡最該先上的一課，因為它回答一個學員普遍搞不清楚的問題：
**「提示（prompt）」和「Agent」到底差在哪？**

提示工程師的核心主張是——**提示就是規格（spec）**。模型沒照做，不是模型爛，是規格模糊。
它把「隨手打一句話問 AI」提升到「定義輸出格式、成功標準、測試案例、版本」的工程行為。

而一個 **Agent**，就是「一份寫好的規格（系統提示）＋ 專業流程 ＋ 明確交付物」被固定下來、
可以重複召喚。學員理解了提示工程師在幹嘛，就理解了這門課後面所有數位員工的本質。

一句話：**它把「一次性的一句話」提升到「可測試、可版本控管的契約」。**

### 什麼時候召喚它

- 某個提示時好時壞，要把它做穩
- 要把一段常用的 AI 用法固定成團隊資產
- 換模型後行為跑掉，要建迴歸測試
- 擔心提示被使用者輸入注入、繞過

### 什麼時候「不要」召喚它

- 只是要問一個一次性問題、用完即丟 → 直接問就好
- 問題是「這個任務適不適合用 LLM」→ ai-engineer

## 2. Before / After 示範

**任務**：「幫我寫一個把客訴分類的提示。」

### Before（無 Agent）

> 產出：「你是一個客服助理，請把以下客訴分類。」——沒有定義有哪些類別、
> 輸出要什麼格式、遇到看不懂的內容怎麼辦。換個月測就飄。

### After（召喚 prompt-engineer）

> 產出會包含：
> - 先問清楚：輸出格式（JSON？固定列舉？）、最常見的 3 種輸入、哪些要拒絕
> - 用「角色 → 約束 → 推理 → 範例」結構寫的系統提示
> - 至少 3 個測試案例：正常路徑、邊界（空輸入／注入）、失敗模式
> - 變更紀錄格式（v1/v2…）與「測試時用的模型、temperature」
> - 一段「已知限制」

**課堂提問**：讓學員指出「Before 版本會在什麼情況下失效」，以及 After 版本裡
「哪一項讓這則提示變成可以交給別人維護的東西」（提示：測試案例 + 版本）。

## 3. 怎麼帶學員「驗收」它的產出

| 檢核點 | 有 / 無 |
|---|---|
| 有先定義「預期輸出格式」與「成功標準」，才開始寫提示 | |
| 沒有「要簡潔」「要有幫助」這種模糊詞，都有具體定義 | |
| 至少 3 個測試案例，涵蓋正常 / 邊界 / 失敗 | |
| 有版本與變更紀錄的格式 | |
| 有記錄「測試用的模型 + temperature」 | |
| 有「已知限制」段落 | |
| 對範圍外輸入有明確的備援行為 | |

## 4. 常見誤區

1. **把它當「幫我把句子寫漂亮」。** 它的價值在「把提示變成有測試、有版本的規格」，
   不是修辭。
2. **跳過「先問清楚」那一步。** 學員急著要成品，但這個 Agent 的方法論第一步就是反問
   輸出格式與邊界——那一步才是重點。
3. **一次改一堆。** 定義明講「一次只修一個問題」，不然無法判斷是哪個改動有效。
4. **提示寫死在程式碼裡。** 定義要求提示進版本控管，當獨立檔案。

## 5. 銜接其他 Agent

提示工程師教會學員「Agent = 固定下來的規格」。接著：
- **ai-engineer** 判斷「這個任務到底該不該用 LLM」
- **multi-agent-systems-architect** 處理「多個這種規格怎麼分工協作」
這三個合起來，就是模組 1 的觀念核心：**Agent 是什麼、何時用、怎麼組。**
