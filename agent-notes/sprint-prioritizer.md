# 教學導引：Sprint 優先排序師（sprint-prioritizer）

- **模組**：3 — 產品
- **能力層**：L3（會編）
- **對應 Agent 定義**：[`AI-to-Agent-Agency-zh-TW` / `agents/product/sprint-prioritizer.md`](https://github.com/draiagent/AI-to-Agent-Agency-zh-TW/blob/main/agents/product/sprint-prioritizer.md)

---

## 1. 定位：這個 Agent 解決什麼問題

product-manager 決定「做什麼、成功怎麼衡量」。Sprint 優先排序師負責更細一層：
**在有限的團隊產能裡，這個 sprint 到底先裝哪幾個故事？** 它用框架（RICE、
價值對工作量矩陣、Kano 模型）把「大家都覺得很重要」變成一個有序、有數字、可辯護的清單。

它也管兩件學員常忽略的事：**產能規劃**（歷史產能、休假、會議開銷、緩衝）與
**相依化解**（95% 在 sprint 開始前解決）。

一句話：**它把「這個也要那個也要」提升到「基於產能與框架，這個 sprint 就做這幾個」。**

### 什麼時候召喚它

- Sprint 規劃、待辦清單排序
- 一堆功能點子要用框架排優先序
- 團隊產能忽高忽低，要做容量預估
- 跨團隊相依要在 sprint 前理清

### 什麼時候「不要」召喚它

- 是「這個功能到底該不該做」的策略問題 → product-manager
- 是「使用者要什麼」→ ux-researcher

## 2. Before / After 示範

**任務**：「下個 sprint 我們要做這 8 件事。」

### Before（無 Agent）

> 產出：把 8 件事都排進去。沒算團隊實際產能、沒留緩衝、相依沒理、
> 沒有 sprint 目標。結果 sprint 末 3 件沒做完，變成技術債。

### After（召喚 sprint-prioritizer）

> 會產出：
> - 用 RICE / 價值對工作量把 8 件排序，附分數
> - 產能評估：6 sprint 滾動平均 − 休假/會議開銷 − 15% 緩衝 = 實際可承諾點數
> - 只裝進得去的（可能是 5 件），其餘明確延後
> - 一個清楚可衡量的 sprint 目標
> - 相依清單：哪幾件卡在別的團隊，要在 sprint 前解決

**課堂提問**：讓學員指出「Before 為什麼註定 sprint 末爆掉」，以及 After 的哪一項
最能防止（提示：產能 − 緩衝）。

## 3. 怎麼帶學員「驗收」它的產出

| 檢核點 | 有 / 無 |
|---|---|
| 有用明確框架排序（RICE / 價值對工作量 / Kano），附分數或分類 | |
| 有算團隊實際產能（歷史平均 − 開銷 − 緩衝），不是「感覺做得完」 | |
| 承諾的量 ≤ 實際產能，且留了緩衝 | |
| 有一個清楚、可衡量的 sprint 目標 | |
| 相依有列出，且有「sprint 前解決」的計畫 | |
| 沒進這個 sprint 的，有明確去向（延後到哪、為什麼） | |

若承諾量 = 待辦全部、沒留緩衝 → 退回。

---

## 4. 常見誤區

1. **產能當「工作時數」。** 要扣會議、站會、context switching、休假，通常只剩 60-80%。
2. **不留緩衝。** 穩定團隊也要 10-15%，因為一定有意外。
3. **框架當儀式。** RICE 分數要有依據（觸及來自分析數據、信心來自訪談），不是隨手填。
4. **相依 sprint 中才發現。** 定義要求 95% 在 sprint 前解決。
5. **沒有 sprint 目標。** 一堆故事湊在一起不是目標；「讓新使用者能在 5 分鐘內完成設定」才是。

## 5. 銜接其他 Agent

product-manager（做什麼、成功指標）→ **sprint-prioritizer（這個 sprint 先做哪幾個、
產能夠不夠）** → 工程數位員工（backend-architect / frontend-developer / …）執行 →
每日站會回報阻礙。在模組 3，這兩個產品數位員工示範「決策」與「排程」是兩個不同職能，
都能被規格化、被驗收。
