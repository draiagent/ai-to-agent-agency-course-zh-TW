# 教學導引：後端架構師（backend-architect）

- **模組**：2 — 工程實作四人組
- **能力層**：L2→L3（會驗 → 會編）
- **對應 Agent 定義**：[`AI-to-Agent-Agency-zh-TW` / `agents/engineering/backend-architect.md`](https://github.com/draiagent/AI-to-Agent-Agency-zh-TW/blob/main/agents/engineering/backend-architect.md)

## 1. 定位：這個 Agent 解決什麼問題

學員常見的狀態是：能請 AI「寫一段 API」，但無法判斷這段設計在**規模變大、資料要改結構、
服務要拆開**時會不會垮。後端架構師這個角色的價值不在「產出程式碼」，而在**產出可被審查的
設計決策**：架構模式怎麼選、資料庫綱要怎麼演進、對外呼叫的逾時／重試／冪等怎麼定。

一句話：**它把「寫得出來」提升到「撐得住」。**

### 什麼時候召喚它

- 要開新服務，得先決定單體 / 模組化單體 / 微服務
- 資料表要改結構，且線上有流量（零停機遷移）
- 系統偶發逾時、雪崩，要補可靠性設計（斷路器、DLQ、艙壁隔離）
- 要寫或審 API 契約（OpenAPI / AsyncAPI）

### 什麼時候「不要」召喚它

- 只是要一個一次性腳本、demo、練習題 → 用 rapid-prototyper
- 純前端互動問題 → 用 frontend-developer
- 還沒有任何規模／可靠性需求的個人專案 → 它會讓你過度設計

## 2. Before / After 示範

**任務**：「幫我做一個訂單服務的 API。」

### Before（無 Agent，一般對話式使用）

> 產出：一段 Express 路由 + 一張 `orders` 資料表。能跑，但沒有版本控管、
> 沒有逾時與重試、金流呼叫失敗會直接 500、改綱要要停機。

### After（召喚 backend-architect）

> 產出會包含：
> - 架構模式選擇與理由（為何先用模組化單體而非微服務）
> - `orders` 綱要 + 索引，含 `expand-and-contract` 遷移步驟
> - 對金流的呼叫：逾時預算、帶退避的重試、冪等鍵
> - 失敗處理：DLQ、毒訊息、對帳檢查
> - OpenAPI 契約片段，含 `429` / `503` 的語意

**課堂提問**：讓學員指出 After 版本裡「哪三項是 Before 版本完全沒有、但上線後一定會用到的」。

## 3. 怎麼帶學員「驗收」它的產出

給學員一份這個 Agent 產出的架構文件，請他們用下列檢核表打分：

| 檢核點 | 有 / 無 |
|---|---|
| 架構模式的選擇**有寫理由**，不是預設微服務 | |
| 每個對外呼叫都有逾時 + 重試 + 冪等 | |
| 綱要變更有零停機遷移步驟（不是「直接 ALTER」） | |
| 錯誤回應標準化（分頁、錯誤碼、關聯 ID） | |
| 有可觀測性設計（結構化日誌、SLI/SLO、追蹤），且圍繞使用者症狀 | |
| 安全：最小權限、靜態與傳輸中加密 | |

少於 4 項打勾 → 要求 Agent 補齊再收。

## 4. 常見誤區

1. **把它當 code generator。** 它的交付物是「設計 + 契約 + 遷移策略」，程式碼只是附帶。
   學員若只複製它的 SQL 就跑，會錯過重點。
2. **無條件接受「微服務」。** Agent 定義裡明確寫「只有效益蓋過維運複雜度才拆」。
   若產出直接給微服務又沒講理由，那是要退回的訊號。
3. **跳過遷移安全。** 學員最容易忽略 `expand-and-contract`、雙寫、回填。
   Lab 第 2 題就是專門練這個。
4. **可觀測性做成「監控 CPU」。** 定義要求「圍繞影響使用者的症狀」，不是只看基礎設施資源。

## 5. 銜接下一個 Agent

後端架構師產出設計 → **code-reviewer** 審實作是否符合設計 →
**devops-automator** 負責部署與 CI/CD。模組 2 的四人組合起來就是一條
「設計 → 實作審查 → 上線」的最小流程，模組 3 之後再往「多 Agent 編排」延伸。
